CONTEXT / THE SHORT VERSION

The Architectural Evolution: Why are there four?

01

SOAP

Born for early Enterprise and Banking systems that needed a strict contract—like a notarized agreement. Reliable and precise, but cumbersome.

02

REST

Freed the web by using simple, familiar HTTP. It is like choosing an item by number from a menu: visible, predictable and easy to use.

03

GraphQL

Arrived when mobile apps received too much data (over-fetching) or needed too many requests (under-fetching). The client can ask for exactly the fields it needs.

04

gRPC

Built for internal microservices that need maximum speed. It packs data into binary Protobuf and sends it over the high-speed HTTP/2 highway.

BEGINNER TOOLKIT

Beginner Jargon Buster

WSDL (SOAP)

Think of it as the blueprint for a strict agreement: it specifies exactly which function to call and which data types are required.

Over-fetching vs Under-fetching

Over-fetching is asking for a name but receiving the whole family history. Under-fetching is calling the server three times to collect an avatar, profile and grades for one screen.

Protocol Buffers (gRPC)

Data is compressed into binary (0s and 1s) so machines can read it quickly, instead of using human-readable JSON text.

HTTP/2 Multiplexing

Several data streams can travel in parallel over one connection, like multiple lanes sharing one highway instead of opening a new queue for each request.

02 / THE DECISION

We pick REST.

For a Student Management System, boring is beautiful. REST gives students, staff and third-party tools a shared language they already understand: HTTP.

Good architecture makes the right thing feel obvious.

01

Everyone speaks HTTP

Browsers, mobile apps and campus integrations can jump in without a specialist client.

02

Clear resources

Students, courses and enrollments map cleanly to URLs and verbs: GET, POST, PATCH, DELETE.

03

Easy to debug

Readable JSON plus familiar status codes make testing in Postman or a browser a breeze.

04

Grows with the campus

Stateless requests, caching and versioned endpoints keep future releases flexible.

THE COUNTERARGUMENT

Why NOT the others for this portal?

Why not SOAP?

Too heavy for a student-facing web frontend; the XML envelope adds latency the portal does not need.

Why not GraphQL?

Student systems mostly use fixed CRUD operations such as course enrollment and grade lookup. GraphQL would add server governance and more complex caching.

Why not gRPC?

Browsers do not support native gRPC directly; they need a gRPC-Web proxy. It fits internal service-to-service communication better than this client portal.
