01 / KHÁI NIỆM CỐT LÕI

Bốn con đường, bốn cách trả lời.

Không có API nào luôn thắng. Mỗi kiểu tối ưu cho một cách giao tiếp, một nhóm client và một tập ràng buộc khác nhau.

01

SOAP

Giao thức có hợp đồng chặt, thường dùng XML và WSDL. Nó phù hợp với quy trình doanh nghiệp cần tính quy chuẩn, nhưng phần thông điệp khá nặng.

02

REST

Phong cách tổ chức tài nguyên trên HTTP. REST dễ tiếp cận với web và mobile, hỗ trợ cache tốt, nhưng cần thiết kế resource và status code cẩn thận.

03

GraphQL

Client gửi query để lấy đúng trường dữ liệu cần. Cách này giảm over-fetching và under-fetching, đổi lại server phải quản lý schema và độ phức tạp của query.

04

gRPC

Framework gọi hàm từ xa, thường dùng Protocol Buffers trên HTTP/2. gRPC mạnh cho giao tiếp service-to-service, nhưng không phải lựa chọn trực tiếp, tự nhiên nhất cho browser.

BỘ CÔNG CỤ CHO NGƯỜI MỚI

Giải thích thuật ngữ

WSDL

Bản mô tả hợp đồng của SOAP: operation nào tồn tại và kiểu dữ liệu nào được chấp nhận.

Over-fetching / under-fetching

Nhận thừa dữ liệu hoặc phải gọi nhiều request mới đủ dữ liệu cho một màn hình.

Protocol Buffers

Định dạng nhị phân do schema mô tả, thường nhỏ và nhanh hơn text trong giao tiếp giữa service.

HTTP/2 multiplexing

Nhiều stream có thể đi qua một connection, giảm việc phải mở hàng đợi riêng cho từng request.

03 / KẾT LUẬN CÓ ĐIỀU KIỆN

Mình nghiêng về REST.

Trong Student Management System giả định của bài — client web/mobile, nghiệp vụ CRUD và nhu cầu dễ tiếp cận — REST là điểm bắt đầu hợp lý. Đây không phải kết luận đúng cho mọi hệ thống.

“

Kiến trúc tốt khiến quyết định phù hợp trở nên dễ nhìn thấy.

— Ghi chép học tập về kiến trúc API
01

Client quen với HTTP

Browser, mobile app và công cụ tích hợp có thể bắt đầu mà không cần client chuyên biệt.

02

Resource rõ ràng

Student, course và enrollment có thể ánh xạ tự nhiên vào URL và HTTP verbs.

03

Dễ quan sát

JSON dễ đọc cùng status code quen thuộc giúp việc kiểm tra request rõ ràng hơn.

04

Còn chỗ để phát triển

Stateless request, cache và versioned endpoint tạo nền tảng để hệ thống tiến hóa.

GÓC NHÌN ĐỐI LẬP

Vì sao chưa chọn ba phương án còn lại?

SOAP

Hợp đồng chặt hữu ích, nhưng XML envelope có thể là phần nặng không cần thiết cho portal sinh viên.

GraphQL

Linh hoạt về field, nhưng bài toán CRUD giả định chưa nhất thiết cần thêm chi phí quản lý query và cache.

gRPC

Rất hợp với service nội bộ; browser thường cần gRPC-Web proxy nên đường đi đến client portal dài hơn.

05 / GÓC NHÌN CÁ NHÂN

Điều bài viết
giúp mình hiểu.

Vì sao mình viết

Mình muốn biến bốn cái tên quen thuộc thành một bài tập ra quyết định dễ theo dõi khi học backend và thiết kế hệ thống.

Mình học được gì

Kiểu API nên bắt đầu từ ràng buộc: client, dữ liệu, hiệu năng, governance và cách team vận hành hệ thống.

Khuyến nghị của mình

Với portal sinh viên hư cấu, nhiều CRUD và phục vụ web/mobile, REST là điểm bắt đầu dễ giải thích và dễ kiểm tra.

Nếu làm một project FPTU

Mình sẽ bắt đầu bằng REST API có tài liệu rõ ràng, rồi xem lại lựa chọn khi domain và traffic trở nên cụ thể hơn.

GZU, GZU-2048, CS101 và các mã enrollment trong bài đều là ví dụ hư cấu.
